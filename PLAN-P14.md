**Plik:** `shared/microservice-email/src/main/java/com/jrobertgardzinski/mail/boundary/DlqResource.java:44-46 (oraz MailRequestsConsumer.java:128-132)`

### WYSOKI

#### P14-02. Awaria brokera dłuższa niż ~18 h trwale zatruwa cały backlog — licznik attempts nie odróżnia timeoutu od odrzucenia  ← **kod z 2026-07-28**

**Plik:** `/home/robert/Documents/git/shared/transactional-outbox/src/main/java/com/jrobertgardzinski/outbox/OutboxRepublisher.java:90 oraz TransactionalOutbox.java:87`

**Objaw:** Mechanizm trucizny jest pomyślany dla przyczyn per-wiersz (payload > max.request.size, skasowany temat, ACL), ale attempts rośnie także wtedy, gdy publishAndWait kończy się TIMEOUTEM przy leżącym brokerze (patience 5 s < delivery.timeout 30 s, więc przy outage każdy re-send kończy się timeoutem bez callbacku). Suma backoffów do 25. próby: 30+60+120+240+480+960+1920 s + 17×3600 s ≈ 18,1 h. Awaria brokera (albo sieci do niego) trwająca dłużej — weekendowy incydent — powoduje, że KAŻDY wiersz z początku awarii osiąga attempts=25 i predykat 'attempts < ?' wyklucza go NA ZAWSZE; po naprawie brokera backlog nie wychodzi, obietnica 'will eventually reach the broker' jest złamana, a jedynym ratunkiem jest ręczny UPDATE zerujący attempts (nie ma żadnego narzędzia ani ścieżki operacyjnej). Wariant drugi: broker jedynie WOLNY (ack po 6-10 s > patience 5 s) — event faktycznie dochodzi, a mimo to attempts rośnie; po 25 takich passach wiersz dostarczony ~25 razy zostaje oznaczony jako trucizna z ERROR-em w logu.

**Dowód:** TransactionalOutbox.java:84-87: selectPendingSql = "... WHERE published_at IS NULL AND created_at <= ? AND (next_attempt_at IS NULL OR next_attempt_at <= ?) AND attempts < ? ..."; OutboxRepublisher.java:90-92: "int attempts = outbox.recordFailedAttempt(event.id(), ...); if (attempts >= settings.poisonAfter())" — wywoływane dla KAŻDEGO false z publishAndWait; OutboxPublisher.java:164-170: "catch (Exception notConfirmed) { // TimeoutException ... return false; }" — timeout i odrzucenie zwracają to samo false. RepublisherSettings.java:100-101: defaults = patience 5 s, backoffBase 30 s, cap 1 h, poisonAfter 25.

**Naprawa:** Zmienić kontrakt publishAndWait z boolean na wynik trójwartościowy {CONFIRMED, TIMED_OUT, REJECTED} (TIMED_OUT = TimeoutException/Interrupted z settled.get, REJECTED = jawny failed(...) od producenta lub sendRefused). W OutboxRepublisher.runOnce inkrementować attempts (a więc i zbliżać do trucizny) tylko dla REJECTED; dla TIMED_OUT ustawiać wyłącznie next_attempt_at (backoff bez licznika). To zachowuje ochronę głowy kolejki, a przestaje zamieniać awarię brokera w trwałą utratę dostarczeń.

**Korekta weryfikatora:** Trzy precyzje, istota bez zmian: (1) ~18,1 h to DOLNA granica — przy leżącym brokerze pass kosztuje do 500×5 s patience (~42 min), więc kadencja prób jest ograniczona także passami i realny czas do zatrucia jest dłuższy; (2) zatruwanie idzie falami oldest-first po resendBatchRows=500 wierszy, więc 'KAŻDY wiersz z początku awarii' to najstarsze 500 na falę, nie cały backlog naraz; (3) wariant wolnego brokera dotyczy tylko re-sendów republishera (pierwsza próba nie czeka) i wymaga acku trwale > 5 s. Nic nie jest skasowane (wiersze zostają, jest ERROR per wiersz), a ratunek to jeden ręczny UPDATE — ale ścieżki operacyjnej ani narzędzia brak, więc waga WYSOKI się broni dla biblioteki, której racją bytu jest 'will eventually reach the broker'.

#### P14-03. offline-jwt: przeterminowany cache JWKS omija floor 10 s — fetch HTTP przy KAŻDYM żądaniu podczas awarii security  ← **kod z 2026-07-28**

**Plik:** `/home/robert/Documents/git/shared/offline-jwt/src/main/java/com/jrobertgardzinski/offlinejwt/OfflineJwtVerifier.java:158`

**Objaw:** Gdy security jest niedostępne dłużej niż keysMaxAge (15 min), cache staje się stale i floor przestaje obowiązywać: każde verify() na każdym serwisie-konsumencie wykonuje synchroniczny HTTP GET na /.well-known/jwks.json (connect timeout 3 s, request 5 s). **Dowód:** OfflineJwtVerifier.java:147-162: `boolean stale = clock.get().isAfter(fetchedAt.plus(keysMaxAge)); if (!stale && known.containsKey(kid)) {...} if (!stale && clock.get().isBefore(lastFetchAttempt.plus(refetchFloor))) { return known.get(kid); } lastFetchAttempt = clock.get(); Map<String, PublicKey> fresh = jwksFetcher.get();` — oba strażniki mają prefiks `!stale`, więc przy stale=true fetch idzie bezwarunkowo; przy nieudanym fetchu (`fresh.isEmpty()`) fetchedAt zostaje na starym miejscu (linia 165: "fetchedAt stays put"), więc stale pozostaje true na zawsze. **Korekta weryfikatora:** Trzy poprawki opisu: (1) waga raczej SREDNI niz WYSOKI i to defekt DOSTEPNOSCIOWY, nie wzmacniacz dla atakujacego — anonim ze zmyslonym kid NIE moze wywolac stanu stale (staleness powstaje wylacznie po realnej awarii security >15 min), wiec 'darmowy wzmacniacz' odpada; w oknie awarii fetch wywoluje KAZDE zadanie, takze z poprawnym kid.
